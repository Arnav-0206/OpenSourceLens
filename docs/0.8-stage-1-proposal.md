# OpenSourceLens — Project Specification & Academic Proposal

## 1. Project Title

**OpenSourceLens: A Data Science-Powered GitHub Repository Intelligence Platform**

---

## 2. Project Overview & Executive Summary

OpenSourceLens is an intelligent, data science-driven analytics platform designed to analyze open-source software repositories on GitHub. Moving beyond simple vanity metrics and raw counts, OpenSourceLens applies rigorous data engineering, statistical modeling, machine learning, natural language processing, and semantic vector retrieval to extract deep, evidence-backed intelligence regarding repository evolution, community sustainability, and maintenance dynamics.

The platform is designed to operate with **any eligible public GitHub repository** entered by a user. Users supply a repository URL, and the platform dynamically ingests, structures, and analyzes its commit history, contributor ecosystem, pull request workflows, and issue tracking data.

To validate its analytical pipelines and train universal natural language processing models, OpenSourceLens utilizes an initial benchmark corpus composed of four major open-source ecosystems:
- `microsoft/vscode` (Developer Tools & GUI Application)
- `pytorch/pytorch` (High-Performance Machine Learning Framework)
- `kubernetes/kubernetes` (Cloud-Native Infrastructure & Distributed Systems)
- `huggingface/transformers` (State-of-the-Art Deep Learning & NLP)

These four repositories serve as our benchmark laboratory and validation baseline; they do not define the functional boundaries of the end product.

---

## 3. Problem Statement & Motivation

Open-source repositories are the foundational infrastructure of modern software engineering. Platforms like GitHub provide extensive raw data: commit lists, contributor rosters, open pull requests, and issue trackers. However, raw data is not actionable intelligence:

| Raw GitHub Metric | The OpenSourceLens Derived Intelligence |
|---|---|
| Total Commit Count | Time-series activity trends, rolling velocity, momentum shifts, sprint bursts, and stagnation anomalies |
| Contributor List | Gini coefficient concentration, Shannon entropy, bus-factor vulnerability, core vs. peripheral community segmentation, newcomer retention |
| Open Pull Requests | PR lifecycle turnaround, review response velocity, merge ratio, abandonment rate, and code-review bottleneck detection |
| Issue List & Labels | Domain-agnostic taxonomy classification (Bug vs Feature vs Other), semantic duplicate detection, backlog aging, and inflow vs outflow balance |
| Repository Statistics | Cross-domain intelligence synthesis: Correlating contributor attrition with PR slowdowns and rising bug volume to diagnose project health |

Understanding these underlying dynamics is critical for multiple stakeholders:
- **Developers & Contributors:** Evaluating project health, responsiveness to pull requests, and maintenance sustainability before investing effort.
- **Maintainers & Tech Leads:** Identifying triage bottlenecks, contributor drop-off, backlog accumulation, and review latency.
- **Researchers & Students:** Investigating empirical software engineering trends, open-source governance models, and cross-repository machine learning generalization.

OpenSourceLens addresses this gap by pairing automated, rate-budgeted GitHub data ingestion with advanced statistical analysis and fine-tuned machine learning models exposed through an interactive web application.

## 4. Project Objectives

### 4.1 Primary Objective
To design, implement, and evaluate an end-to-end repository intelligence platform that dynamically collects public GitHub repository data, extracts statistical and machine-learning-driven insights across six analytical domains, and presents actionable findings through an interactive web dashboard.

### 4.2 Supporting Technical Objectives
1. **Dynamic Data Ingestion & Budgeting:** Implement an asynchronous data collection pipeline that ingests commits, contributors, pull requests, issues, and releases from any eligible public repository while strictly respecting GitHub API rate limits.
2. **Relational Data Modeling:** Design a normalized, database-agnostic schema (PostgreSQL / SQLite) supporting both dynamic analytical queries and audit logging of machine learning predictions.
3. **Development Time-Series Analytics:** Implement moving averages, trend decomposition, burstiness metrics, and anomaly detection to evaluate repository momentum.
4. **Contributor Ecosystem Modeling:** Compute Gini coefficients, Lorenz curves, Shannon entropy, and retention half-life to quantify community concentration and bus-factor risks.
5. **Pull Request Lifecycle Analysis:** Model review turnaround times, merge durations, and file-change size correlation to uncover maintenance bottlenecks.
6. **Universal Issue Classification:** Establish classical machine learning baselines (TF-IDF + Logistic Regression/SVM) and fine-tune a universal transformer model (`distilbert-base-uncased`) capable of domain-agnostic taxonomy prediction (`bug`, `feature`, `other`).
7. **Dense Semantic Retrieval:** Implement Sentence-Transformers (`all-MiniLM-L6-v2`) to map issue descriptions into a 384-dimensional vector space for semantic similarity and duplicate retrieval.
8. **Issue Resolution Velocity Modeling:** Statistically evaluate resolution durations, empirical turnaround percentiles, and Kaplan-Meier survival curves across SLA speed tiers.
9. **Cross-Domain Intelligence Synthesis:** Develop an automated diagnostic engine that correlates signals across activity, contributor, PR, and issue domains to generate narrative, evidence-backed findings.
10. **Interactive Web Application:** Build a production-ready Next.js 15 / React 19 frontend paired with a high-concurrency FastAPI backend.
11. **Empirical Evaluation & Generalization:** Benchmark models using Leave-One-Repository-Out (LORO) cross-validation on the benchmark corpus and verify inference stability on unseen repositories.

## 6. Machine Learning & Data Science Methodology

### 6.1 Dual-Track Architecture
- **Track A (Offline Benchmark Lab):** Deep historical data collection on four benchmark repositories (`microsoft/vscode`, `pytorch/pytorch`, `kubernetes/kubernetes`, `huggingface/transformers`). Used to train and evaluate classical ML baselines, fine-tune DistilBERT, calibrate semantic similarity thresholds, and establish empirical reference baselines.
- **Track B (Online Dynamic Ingestion & Intelligence):** Real-time ingestion, feature extraction, time-series analysis, contributor concentration modeling, and universal model inference for any public repository requested by an end-user.

### 6.2 Generalization Principles
To ensure models and analytical metrics work effectively on any repository:
- **Universal Vocabulary & Subwords:** DistilBERT WordPiece tokenization handles specialized software vocabulary without out-of-vocabulary degradation.
- **Domain-Agnostic Feature Sets:** Elimination of repository-specific identifiers, flags, or hardcoded rules from inference pipelines.
- **Relative Benchmarking:** Repository health indicators are evaluated against standardized percentile distributions derived from the benchmark corpus.

- **Frontend:** Next.js 15.5 (App Router), React 19, TypeScript 5.7, Tailwind CSS 3.4, Recharts 3.10.
- **Backend API:** FastAPI 0.162, Pydantic v2, Uvicorn, SQLAlchemy 2.0 ORM.
- **Database:** PostgreSQL (Production) / SQLite (Development & Local Testing with WAL mode).
- **ML & Data Science:** PyTorch 2.14, Hugging Face Transformers 4.49, Sentence Transformers 3.4, scikit-learn 1.4, Pandas 2.2, SciPy, Statsmodels.
- **External API:** GitHub REST API v3 with authenticated token rotation and rate-limit budgeting.
