# OpenSourceLens — Stage 1 Project Proposal

## 1. Project Title

**OpenSourceLens: An Intelligent Analytics Platform for GitHub Repository Issues Using Machine Learning and Natural Language Processing**

## 2. Project Overview

OpenSourceLens is a data-driven web application designed to analyze GitHub repositories and their issues using data analytics, classical machine learning, natural language processing, and transformer-based deep learning.

The platform will collect issue-related information from selected open-source repositories, process the collected data, and extract meaningful patterns from repository activity.

It will provide repository-level analytics, automated issue classification, semantic retrieval of potentially related issues, and issue resolution analysis through an interactive web dashboard.

The project combines a complete data science workflow with a deployed software application, allowing users to explore repository data and obtain AI-assisted insights.

## 3. Problem Statement

Open-source software repositories can accumulate large numbers of issues over time. These issues contain valuable information about software defects, feature requests, documentation problems, user questions, and project activity.

However, understanding this information can become difficult when issues, labels, discussions, and timestamps are distributed across a large repository.

Manually examining issues to identify common categories, discover related discussions, understand activity patterns, and investigate resolution behavior can be time-consuming.

OpenSourceLens aims to address this problem by developing a data-driven platform that combines repository analytics, machine learning, natural language processing, and semantic similarity to make GitHub issue information easier to explore and understand.

## 4. Objectives

### 4.1 Main Objective

To develop an intelligent analytics platform that uses GitHub repository data, machine learning, and natural language processing to analyze software issues and provide meaningful insights through an interactive web application.

### 4.2 Supporting Objectives

1. Collect repository and issue data from selected GitHub repositories.
2. Clean, preprocess, and structure the collected data.
3. Perform exploratory data analysis to identify issue patterns and activity trends.
4. Develop a classical machine-learning model for issue classification.
5. Fine-tune and evaluate a transformer-based issue classifier.
6. Compare classical machine-learning and transformer-based classification approaches.
7. Retrieve potentially related issues using semantic embeddings and similarity measures.
8. Analyze issue resolution times and repository-level resolution patterns.
9. Integrate the analytical and ML/NLP components into a web application.
10. Evaluate the system using suitable metrics and document its limitations.

## 5. Proposed Features

### 5.1 Repository Overview

Display repository information and statistics, including:

- Repository metadata
- Total, open, and closed issue counts
- Issue activity trends
- Issue label distribution
- Issue creation and closure trends

### 5.2 Issue Analytics

Analyze issue data to identify:

- Common issue categories
- Open and closed issue distributions
- Changes in issue activity over time
- Label distribution
- Resolution-time patterns
- Differences between repositories

### 5.3 AI-Based Issue Classification

Predict the category of a GitHub issue using its title and description.

Candidate categories include:

- Bug
- Feature Request
- Documentation
- Question
- Enhancement
- Other

The final categories will depend on the quality and availability of labeled data.

The project will compare:

- **Classical ML:** TF-IDF with Logistic Regression and/or Support Vector Machine.
- **Deep Learning:** A fine-tuned pretrained transformer such as DistilBERT or BERT.

### 5.4 Related-Issue Detection

Identify potentially related issues by generating sentence embeddings and comparing them using cosine similarity.

The system will return a ranked list of potentially related issues to help users discover existing discussions.

### 5.5 Resolution Analysis

Analyze the time taken to close issues using creation and closure timestamps.

The analysis will include resolution-time distributions, average and median resolution times, and comparisons across categories or repositories.

Resolution-time prediction may be explored as an optional extension if the collected data supports reliable modeling.

### 5.6 Interactive Web Dashboard

Provide a web interface through which users can explore repository statistics, inspect analytical visualizations, classify issue text, discover related issues, and examine resolution patterns.

## 6. Dataset and Data Sources

The primary data source will be the GitHub REST API.

The initial candidate repositories are:

1. `microsoft/vscode`
2. `pytorch/pytorch`
3. `kubernetes/kubernetes`
4. `huggingface/transformers`

These repositories represent developer tools, machine learning, cloud infrastructure, and natural language processing.

The collected data may include:

- Repository metadata
- Issue titles and descriptions
- Issue states and labels
- Issue creation, update, and closure timestamps
- Comment metadata and content where appropriate

The repositories are initial candidates. Their final suitability will be validated during data collection and exploratory data analysis.

The number of collected issues and the final dataset size will be determined after evaluating data availability, label quality, and practical collection constraints.

## 7. Proposed Methodology

The project will follow these stages:

1. **Data Collection:** Retrieve repository and issue information using the GitHub API.
2. **Data Preprocessing:** Clean the collected data, handle missing values, normalize labels, and construct structured datasets.
3. **Exploratory Data Analysis:** Investigate issue distributions, activity trends, category balance, and resolution times.
4. **Classical ML Baseline:** Train a TF-IDF-based classifier using Logistic Regression and evaluate an SVM alternative.
5. **Transformer-Based Classification:** Fine-tune a pretrained transformer model for issue classification.
6. **Model Evaluation:** Compare classification models using accuracy, precision, recall, F1-score, macro-F1, and confusion matrices.
7. **Related-Issue Detection:** Generate sentence embeddings, calculate cosine similarity, and retrieve potentially related issues.
8. **Resolution Analysis:** Examine resolution-time distributions and differences across issue categories and repositories.
9. **Application Integration:** Connect the data, analytics, and model components to the web application.
10. **Deployment and Testing:** Deploy the application, test its main features, and document the results and limitations.

## 10. Evaluation Strategy

The project will evaluate its components using task-appropriate methods.

### Issue Classification

The classical and transformer-based classifiers will be evaluated using:

- Accuracy
- Precision
- Recall
- F1-score
- Macro-F1
- Confusion matrix

### Related-Issue Detection

The retrieval system will be evaluated using suitable relevance judgments or proxy labels where available.

Potential metrics include Precision@K, Recall@K, and Mean Reciprocal Rank.

### Resolution Analysis

The analysis will use descriptive statistics, distributions, and comparisons across relevant categories and repositories.

### Application Evaluation

The final application will be tested for:

- Correctness of displayed analytics
- Validity of model predictions and retrieval results
- API and database integration
- Handling of invalid inputs and errors
- Usability and responsive presentation
- Deployment reliability

## 12. Scope and Limitations

The initial project focuses on repository analytics, issue classification, related-issue detection, and resolution analysis.

The following are outside the initial scope:

- Automatic issue resolution
- Automatic issue closing
- Automatic developer assignment
- Code generation
- A general-purpose AI chatbot
- Guaranteed duplicate detection

Potential limitations include inconsistent repository labels, class imbalance, missing issue descriptions, differences between repository workflows, API rate limits, and computational requirements for transformer training and inference.

The project will report these limitations and adjust its modeling decisions based on the available evidence.
