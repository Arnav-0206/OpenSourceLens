# OpenSourceLens — Data Definition

## 1. Data Sources

OpenSourceLens will primarily use data collected from the GitHub API.

The project will collect data from selected open-source repositories and use it for repository analytics, exploratory data analysis, machine learning, natural language processing, related-issue detection, and resolution analysis.

The main data categories are:

- Repository data
- Issue data
- Comment data
- Label data
- Temporal and resolution data

---

## 2. Repository Data

Basic information about each selected repository will be collected.

Important fields include:

- `repository_name`
- `owner`
- `description`
- `language`
- `stars`
- `forks`
- `open_issues_count`
- `created_at`
- `updated_at`

Repository data will primarily support repository-level analytics and comparisons.

---

## 3. Issue Data

Issue data is the primary dataset for the project.

For each issue, the following information will be collected where available:

- `issue_id`
- `issue_number`
- `repository`
- `title`
- `body`
- `state`
- `author`
- `labels`
- `created_at`
- `updated_at`
- `closed_at`
- `comments_count`

Issue data will be used for:

- Issue analytics
- Issue classification
- NLP processing
- Related issue detection
- Resolution analysis

---

## 4. Comment Data

Comments provide additional context about discussions surrounding an issue.

For each comment, the following information may be collected:

- `comment_id`
- `issue_id`
- `author`
- `body`
- `created_at`
- `updated_at`

Comments will initially be retained as additional repository information.

They will not automatically be included in the issue-classification model. Their usefulness will be evaluated during data exploration and experimentation.

---

## 5. Label Data

GitHub labels provide information about how maintainers categorize issues.

Relevant fields include:

- `issue_id`
- `label_name`

Examples of labels may include:

- `bug`
- `enhancement`
- `documentation`
- `question`
- `feature`
- `help wanted`
- `good first issue`

Labels will be used for exploratory analysis and may contribute to the construction of classification categories.

Care will be taken to avoid data leakage when labels are used as classification targets.

---

## 6. Temporal and Resolution Data

Time-related fields are important for understanding issue activity and resolution behavior.

The primary fields are:

- `created_at`
- `updated_at`
- `closed_at`

For closed issues, a derived feature called `resolution_time` will be calculated:

This will allow analysis of:

- Average resolution time
- Median resolution time
- Resolution-time distribution
- Resolution time by issue category
- Resolution time across repositories
- Factors associated with faster or slower resolution

Open issues will not have a final observed resolution time.

---

## 7. Raw Data and Processed Data

The original data received from GitHub will be preserved as raw data.

The data pipeline will follow:

```
GitHub API
    ↓
Raw Data
    ↓
Data Cleaning
    ↓
Data Transformation
    ↓
Processed Dataset
    ↓
EDA + ML + NLP + DL
```

The raw dataset will not be directly modified during preprocessing.

This allows the project to reproduce the processing pipeline and return to the original data if necessary.

---

## 8. Initial Processed Issue Dataset

The main processed issue dataset is expected to contain fields such as:

| Column | Description |
| --- | --- |
| `issue_id` | Unique identifier of the issue |
| `issue_number` | Issue number within the repository |
| `repository` | Repository name |
| `title` | Issue title |
| `body` | Issue description |
| `state` | Open or closed state |
| `author` | Issue creator |
| `labels` | Associated GitHub labels |
| `created_at` | Issue creation timestamp |
| `updated_at` | Last update timestamp |
| `closed_at` | Issue closure timestamp |
| `comments_count` | Number of comments |
| `resolution_time` | Derived time taken to close the issue |

Additional fields may be added or removed after inspecting the actual GitHub API responses.

---

## 9. Data Required by Each Feature

| Feature | Required Data |
| --- | --- |
| Repository Overview | Repository metadata |
| Issue Analytics | Issue metadata, labels, timestamps |
| Issue Classification | Issue title, body, and appropriate target labels/categories |
| Related Issue Detection | Issue title and body |
| Resolution Analysis | Creation and closure timestamps |
| Advanced Analysis | Comments, activity, and additional metadata |

Every collected field should have a clear purpose within the project.

---

## 10. Text Data for NLP

The initial text input for NLP and issue classification will be:

```
Issue Title + Issue Body
```

The title and body will be combined into a suitable text representation during preprocessing.

Comments will initially remain separate from the classification input.

This provides a controlled baseline for evaluating classical NLP and transformer-based approaches.

---

## 11. Issue Categories

Different repositories may use different naming conventions for similar issue types.

For example:

```
Repository A → bug
Repository B → type:bug
Repository C → bug-report
```

Therefore, labels may need to be normalized into consistent categories during the data-cleaning stage.

The final classification categories will be determined after examining the collected repositories and their available labels.

---

## 12. Multiple Repositories

The project will aim to collect data from multiple suitable open-source repositories rather than relying entirely on a single repository.

Using multiple repositories can provide:

- Greater dataset diversity
- More varied issue patterns
- More training examples
- Better evaluation of model performance
- Reduced dependence on the characteristics of a single project

The exact repositories will be selected in Step 0.4.

---

The planned data pipeline is:

```

                        ↓

                        ↓

                        ↓
                Processed Dataset
                        ↓

          ↓             ↓             ↓
```

---

## 14. Data Considerations

Several data-related challenges will be considered during implementation:

- Different repositories may use different labels.
- Some issues may have missing descriptions.
- Some issues may remain open for long periods.
- Some repositories may contain very few useful labeled issues.
- Issue categories may be highly imbalanced.
- GitHub API rate limits may affect data collection.
- Some repositories may contain noisy or low-quality text.
- Labels used as classification targets must be handled carefully to avoid data leakage.

These issues will be addressed during the data collection and data-cleaning phases.

---

## 15. Final Data Objective

The objective of the data pipeline is to create a clean, structured, and sufficiently diverse dataset that can support:

1. Repository-level analytics
2. Exploratory data analysis
3. Classical machine-learning classification
4. Transformer-based issue classification
5. Semantic related-issue detection
6. Issue resolution analysis
7. Further experimentation where the dataset supports it
