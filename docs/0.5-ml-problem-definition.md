# OpenSourceLens — ML Problem Definition

## 1. Objective

OpenSourceLens will use machine learning, natural language processing, and deep-learning-based techniques to analyze GitHub issues and provide meaningful insights into open-source repositories.

The main ML/NLP tasks are:

1. Issue classification
2. Related-issue detection
3. Issue resolution analysis

Resolution-time prediction will be considered an optional extension depending on data quality, dataset size, and experimental results.

---

## 2. Problem 1: Issue Classification

### 2.1 Problem Definition

GitHub repositories contain issues describing bugs, feature requests, documentation problems, questions, and other development-related concerns.

Manually categorizing a large number of issues can be time-consuming.

OpenSourceLens will develop a model that predicts an issue category using the issue's title and description.

### 2.2 Input

The model will initially use:

- Issue title
- Issue description (body)

The title and body will be combined into a text input suitable for NLP processing.

### 2.3 Output

The model will predict one of the following candidate categories:

- Bug
- Feature Request
- Documentation
- Question
- Enhancement
- Other

The final categories will depend on the availability and quality of labeled examples in the collected dataset.

### 2.4 Learning Type

This is a supervised text-classification problem.

The model will learn patterns from issue text paired with reliable category labels.

### 2.5 Classical Machine-Learning Approach

The initial baseline will use:

- Text preprocessing
- TF-IDF feature extraction
- Logistic Regression
- Support Vector Machine (SVM)

The models will be trained and evaluated using a suitable labeled dataset.

### 2.6 Deep-Learning Approach

A pretrained transformer model will be fine-tuned for issue classification.

Candidate architectures include:

- DistilBERT
- BERT

The final model will be selected based on dataset suitability, computational requirements, and evaluation results.

### 2.7 Model Comparison

The classical and transformer-based approaches will be compared using:

- Accuracy
- Precision
- Recall
- F1-score
- Macro-F1
- Confusion matrix

Macro-F1 will be particularly important if the dataset contains imbalanced issue categories.

The comparison will help determine whether transformer-based contextual representations provide a meaningful improvement over the classical NLP baseline.

### 2.8 Data Considerations

The classification dataset will be constructed from issues with sufficiently reliable target labels.

Repository-specific labels will be normalized using documented mapping rules.

Labels representing workflow status, modules, teams, or other metadata will not automatically be treated as issue categories.

The dataset will be inspected for missing text, ambiguous labels, and class imbalance.

Care will be taken to avoid data leakage. For example, labels used to construct the target must not also be supplied to the model as input features.

## 3. Problem 2: Related-Issue Detection

### 3.1 Problem Definition

Large GitHub repositories may contain issues that discuss similar problems, related features, or overlapping technical concerns.

Finding these issues manually can be difficult.

OpenSourceLens will identify potentially related issues by comparing their textual meaning.

### 3.2 Input

The system will initially use:

- Issue title
- Issue description

These fields will be combined into text suitable for embedding generation.

### 3.3 Output

For a selected issue, the system will return a ranked list of potentially related issues.

Each result may include:

- Issue number
- Issue title
- Issue state
- Issue URL
- Similarity score

### 3.4 Method

The planned approach is:

1. Generate sentence embeddings for issue text.
2. Store the embeddings for efficient reuse.
3. Generate an embedding for the selected issue.
4. Calculate cosine similarity against candidate issue embeddings.
5. Rank the candidate issues by similarity.
6. Return the top-K results.

A suitable sentence-transformer model will be selected during implementation.

### 3.5 Evaluation

The retrieval system will be evaluated using suitable relevance judgments or available proxy labels.

Potential evaluation metrics include:

- Precision@K
- Recall@K
- Mean Reciprocal Rank (MRR)

The final evaluation method will depend on the availability of reliable relevance labels.

Similarity scores alone will not be treated as proof that two issues are genuinely related.

The system will present results as potentially related issues rather than definitively identifying duplicates.

## 4. Problem 3: Issue Resolution Analysis

### 4.1 Problem Definition

Understanding how long GitHub issues take to resolve can help users investigate repository activity and issue-management patterns.

OpenSourceLens will analyze resolution times and compare them across relevant categories and repositories.

### 4.2 Required Data

The analysis will use:

- Issue creation timestamp
- Issue closure timestamp
- Issue state
- Issue category or labels
- Repository identifier

Additional metadata may be used where appropriate.

### 4.3 Resolution-Time Calculation

For an issue that has been closed, resolution time will initially be calculated as:

`resolution_time = closed_at - created_at`

The duration may be represented in hours or days.

Open issues will not have a final observed resolution time and will not be assigned an artificial closure duration.

### 4.4 Analysis

The planned analysis includes:

- Average resolution time
- Median resolution time
- Resolution-time distribution
- Resolution time by issue category
- Resolution time across repositories
- Factors associated with faster or slower closure

The analysis will account for the fact that resolution times may be highly skewed and that repository comparisons may be affected by differences in issue types and workflows.

### 4.5 Learning Type

The initial resolution component is a data analytics task rather than a machine-learning prediction task.

It will focus on descriptive statistics, visualizations, and comparisons.

---

## 5. Optional Problem 4: Resolution-Time Prediction

### 5.1 Problem Definition

As an optional extension, OpenSourceLens may estimate how long an issue could take to close using information available when the issue is created.

### 5.2 Candidate Inputs

Potential input features include:

- Issue title and description features
- Issue category, if available at prediction time
- Repository characteristics
- Other metadata available at issue creation

Features that become available only after closure must not be used to predict the original resolution time.

### 5.3 Output

The model would estimate the expected resolution duration for an eligible issue.

### 5.4 Candidate Approach

A simple regression baseline may be compared with a more advanced model if the dataset supports meaningful experimentation.

### 5.5 Evaluation

Potential metrics include:

- Mean Absolute Error (MAE)
- Root Mean Squared Error (RMSE)

The prediction model will only be developed if the available data, evaluation design, and time constraints justify it.

This feature is not required for the initial project scope.

---

## 6. Dataset Preparation and Evaluation Strategy

The following principles will guide the construction and evaluation of the ML datasets:

- Inspect repository-specific label distributions before defining final classification categories.
- Normalize labels using documented mapping rules.
- Remove or appropriately handle issues with unusable text or ambiguous labels.
- Investigate class imbalance before model training.
- Separate training, validation, and test data appropriately.
- Prevent information leakage between training and evaluation sets.
- Use suitable metrics for each task.
- Document limitations and sources of uncertainty.

For classification, issues will be split in a way that reduces the risk of near-identical or duplicated issue text appearing across training and test sets.

Where practical, additional repository-aware evaluation may be considered to investigate how well the classifier generalizes to repositories not represented in its training data.

The exact split strategy will be finalized after examining the collected dataset.

## 7. Summary of ML/NLP Tasks

| Task | Learning or Analysis Type | Planned Method | Priority |
|---|---|---|---|
| Issue Classification | Supervised learning | TF-IDF + Logistic Regression/SVM | Core |
| Transformer Classification | Deep learning | Fine-tuned DistilBERT/BERT candidate | Core |
| Related-Issue Detection | Semantic retrieval | Sentence embeddings + cosine similarity | Core |
| Resolution Analysis | Data analytics | Statistical analysis and visualization | Core |
| Resolution-Time Prediction | Regression | Baseline regression model, if feasible | Optional |

---

## 8. Expected Outcome

The expected outcome is a set of clearly defined analytical and ML/NLP components that can be implemented and evaluated independently before integration into OpenSourceLens.

The project will compare classical and transformer-based issue classification, provide semantic retrieval of potentially related issues, and analyze issue resolution behavior.

All final model choices, category mappings, and evaluation strategies will be supported by observations from the collected data and documented experimental results.
