## 2. API Authentication and Rate Limits

GitHub enforces strict rate limits based on client authentication status:

| Metric | Unauthenticated Requests | Authenticated Requests (`GITHUB_TOKEN`) |
|---|---|---|
| **Rate Limit** | 60 requests / hour | 5,000 requests / hour |
| **Quota Identifier** | Client IP address | GitHub User Account / Token |
| **Limit Endpoint** | `GET https://api.github.com/rate_limit` | `GET https://api.github.com/rate_limit` |
| **Response Headers** | `x-ratelimit-limit`, `x-ratelimit-remaining`, `x-ratelimit-reset` | `x-ratelimit-limit`, `x-ratelimit-remaining`, `x-ratelimit-reset` |

### Key Implementation Principles for Collectors:
1. **Header Inspection:** Every HTTP response returns `x-ratelimit-remaining` and `x-ratelimit-reset` (Unix epoch seconds). Collectors in Step 1.7 must inspect these headers after every batch.
2. **Backoff Threshold:** If `x-ratelimit-remaining` drops below 10, the collector should pause execution until the UTC reset timestamp indicated by `x-ratelimit-reset`.
3. **Token Placement:** The token must be passed via the `Authorization: Bearer <TOKEN>` header.

### 3.2 Issues Endpoint & Critical Pull Request Filtering
- **URL:** `GET https://api.github.com/repos/{owner}/{repo}/issues`
- **Query Parameters:** `state=all`, `per_page=100`, `sort=created`, `direction=asc` (or `desc`)
- **Critical Architectural Finding:**
  > [!IMPORTANT]
  > GitHub treats Pull Requests as issues internally. The `/issues` endpoint **returns both pure issues and pull requests**.
  > Pull Requests contain a top-level `"pull_request"` dictionary:
  > ```json
  > "pull_request": {
  >   "url": "https://api.github.com/repos/microsoft/vscode/pulls/342504",
  >   "html_url": "https://github.com/microsoft/vscode/pull/342504",
  >   "diff_url": "https://github.com/microsoft/vscode/pull/342504.diff",
  >   "patch_url": "https://github.com/microsoft/vscode/pull/342504.patch",
  >   "merged_at": null
  > }
  > ```
  > **Pure issues DO NOT contain the `"pull_request"` key.**
  > 
  > **Collector Rule:** The issue collector (Step 1.3) **must explicitly filter out items where `"pull_request" in item`** to ensure the dataset represents software issues rather than pull requests.

- **Verified Schema Fields (Pure Issue):**

| Field | Type | Example Value | Downstream Usage |
|---|---|---|---|
| `id` | integer | `5921227890` | Global unique issue ID |
| `number` | integer | `342505` | Repository-scoped issue number |
| `title` | string | `"The CoPilot chat no longer shows diffs..."` | NLP input feature |
| `body` | string / null | `"Issue description Markdown..."` | NLP input feature |
| `state` | string | `"open"` or `"closed"` | State analytics |
| `user.login` | string | `"ReinierNL"` | Issue author |
| `labels` | array of objects | `[{"name": "bug", "color": "d73a4a"}]` | Supervised classification targets |
| `created_at` | string (ISO8601) | `"2026-10-19T09:22:22Z"` | Temporal tracking |
| `closed_at` | string / null | `null` (or ISO8601 timestamp) | Resolution time calculation (`closed_at - created_at`) |
| `comments` | integer | `1` | Discussion volume metric |

### 3.4 Events Endpoint
- **URL:** `GET https://api.github.com/repos/{owner}/{repo}/issues/{issue_number}/events`
- **Purpose:** Collect lifecycle activity (Step 1.5).
- **Verified Schema Events:**
  - `closed`: Issue was closed by maintainer/bot.
  - `merged`: PR/commit was linked and closed.
  - `labeled` / `unlabeled`: Issue categorization changed.
  - `assigned`: Developer assigned.
  - `review_requested`, `copilot_work_started`, `head_ref_deleted`.
- **Verified Schema Fields:**
  - `id`: Event ID.
  - `event`: Event name (string).
  - `actor.login`: Username who triggered event.
  - `created_at`: Event timestamp.
  - `commit_id`: Associated Git commit SHA (if any).

## 4. Pagination Mechanics

GitHub returns paginated results with up to `per_page=100` items per request.

### Link Header Protocol
GitHub provides a `Link` HTTP response header containing URLs for adjacent pages:
```http
Link: <https://api.github.com/repositories/41881900/issues?state=all&per_page=100&page=2>; rel="next",
      <https://api.github.com/repositories/41881900/issues?state=all&per_page=100&page=219>; rel="last"
```

### Parsing Recommendation for Step 1.6:
- Using `requests.utils.parse_header_links(response.headers.get("Link", ""))` yields a clean Python list:
  ```python
  # Example:
  # [{'url': '...', 'rel': 'next'}, {'url': '...', 'rel': 'last'}]
  ```
- Continue pagination until `rel="next"` is no longer present in the `Link` header or target quota is reached.

## 5. Cross-Repository Label Taxonomies

During exploration of the four candidate repositories, significant differences in labeling conventions were observed:

| Repository | Primary Taxonomy Style | Observed Examples | Cleaning / Normalization Implication (Phase 2) |
|---|---|---|---|
| `microsoft/vscode` | Prefix characters (`*`) and status markers | `*as-designed`, `*caused-by-extension`, `*dev-question`, `*duplicate`, `new release` | Strip leading asterisks; map `*dev-question` to `Question`. |
| `pytorch/pytorch` | Lowercase keyword tags | `actionable`, `advanced`, `agentic`, `aggregate flaky test issue` | Distinguish triage status flags from functional issue types. |
| `kubernetes/kubernetes` | Hierarchical namespace tags and Unicode/emojis | `area/admin`, `area/api`, `api-review`, `¯\_(ツ)_/¯` | Use namespace prefixes (`kind/bug`, `kind/feature`, `area/*`). Handlers must support UTF-8 encoding. |
| `huggingface/transformers` | CamelCase / Model & Component names | `Accelerate`, `Agents`, `Audio`, `Benchmarks`, `Big Model Inference` | Many labels represent model architectures rather than issue categories; careful category filtering required. |

> [!TIP]
> **Unicode Safety Notice:** Label names in projects like `kubernetes/kubernetes` can include complex Unicode characters (e.g. `¯\_(ツ)_/¯`). All console outputs, file writers, and database connections must enforce `UTF-8` encoding to prevent encoding errors on Windows environments.
