# OpenSourceLens — Repository Selection

## 1. Objective

The objective of repository selection is to identify suitable open-source GitHub repositories whose issue data can support repository analytics, exploratory data analysis, machine learning, natural language processing, related-issue detection, and resolution analysis.

Repositories will be evaluated based on issue volume, label quality, text quality, historical activity, availability of closed issues, and domain diversity.

The final selection will be validated further during data collection and dataset exploration.

## 2. Selected Candidate Repositories

The initial candidate repositories are:

| No. | Repository | Domain | Primary Purpose |
|---|---|---|---|
| 1 | `microsoft/vscode` | Developer tools | Issue classification and general repository analytics |
| 2 | `pytorch/pytorch` | Machine learning and deep learning | Large-scale issue analysis and technical issue classification |
| 3 | `kubernetes/kubernetes` | Cloud infrastructure | Repository analytics and analysis of structured issue labels |
| 4 | `huggingface/transformers` | NLP and AI | Issue classification and analysis of technical issue descriptions |

These repositories provide diversity across developer tools, machine learning, infrastructure, and natural language processing.

## 3. Repository Evaluation Criteria

The repositories will be assessed using the following criteria:

| Criterion | Importance | Reason |
|---|---|---|
| Issue volume | High | Provides sufficient data for analytics and modeling |
| Label quality | Very high | Supports the construction of supervised classification targets |
| Text quality | Very high | Provides useful issue titles and descriptions for NLP |
| Closed-issue history | High | Supports resolution-time analysis |
| Issue-type diversity | High | Helps construct a meaningful classification dataset |
| Repository activity | Medium | Provides useful historical and ongoing activity |
| Data accessibility | High | Determines whether data can be collected reliably |
| Domain diversity | Medium | Enables comparisons across different types of software projects |

## 4. Repository-Specific Rationale

### 4.1 Microsoft VS Code

Repository: `microsoft/vscode`

VS Code is a large, mature developer-tool project with a substantial issue history and a documented issue-triage process.

Its issue types and labels make it a promising candidate for issue classification, repository analytics, and resolution analysis.

Primary purpose:
- General-purpose issue classification
- Issue trend analysis
- Label distribution analysis
- Resolution-time analysis

### 4.2 PyTorch

Repository: `pytorch/pytorch`

PyTorch is a major machine-learning framework with a large issue history and a detailed labeling system.

Its labels include issue-related information as well as module, team, and triage metadata. These distinctions will need to be handled during data cleaning.

Primary purpose:
- Large-scale issue analytics
- Technical issue classification
- Label normalization
- Resolution analysis

### 4.3 Kubernetes

Repository: `kubernetes/kubernetes`

Kubernetes is a large open-source infrastructure project with a structured issue-labeling system.

Its labels provide information about issue types, triage status, and areas of responsibility. The labeling scheme differs from those of the other candidates, making it useful for investigating differences between repository taxonomies.

Primary purpose:
- Repository analytics
- Structured label analysis
- Cross-repository comparisons
- Investigation of label normalization

### 4.4 Hugging Face Transformers

Repository: `huggingface/transformers`

Transformers is a widely used NLP and AI library with technical issue descriptions and issue types such as bugs and feature requests.

It is particularly relevant to the project's NLP and transformer-based classification components.

Primary purpose:
- NLP-oriented issue classification
- Technical text analysis
- Related-issue detection
- Resolution analysis

## 5. Label Normalization Strategy

Different repositories use different labels and naming conventions.

Examples include:

- `bug`
- `kind/bug`
- `feature-request`
- `Feature request`
- `enhancement`
- `documentation`

The project will define a common issue-category taxonomy after examining the collected data.

Potential categories include:

- Bug
- Feature Request
- Documentation
- Question
- Enhancement
- Other

A repository-specific mapping will be created to associate reliable source labels with the common categories.

Labels representing modules, teams, workflow status, severity, or other metadata will not automatically be treated as issue-type labels.

Issues with ambiguous or insufficient labeling evidence may be excluded from supervised classification.

## 6. Classification Dataset Considerations

The existence of a large number of issues does not guarantee a large usable classification dataset.

Before training the classification models, the project will investigate:

- The frequency of each issue label
- The number of issues with usable titles and descriptions
- The availability of reliable issue-type labels
- The distribution of categories
- The presence of missing or low-quality text
- Potential label ambiguity
- The possibility of data leakage

Only issues with sufficiently reliable target labels will be included in the supervised classification dataset.

The final category set may be adjusted if some categories have insufficient examples.

## 7. Data Collection Strategy

The selected repositories are initial candidates for data collection.

The exact number of issues to collect from each repository will be determined during Phase 1 after examining API access, pagination, rate limits, data availability, and practical storage requirements.

The project will preserve raw API responses separately from processed datasets.

Repository-specific preprocessing and label mapping will be documented to support reproducibility.

## 8. Limitations and Risks

Potential challenges include:

- Different label conventions across repositories
- Imbalanced issue categories
- Missing issue descriptions
- Noisy or ambiguous labels
- Differences in issue-writing styles across domains
- Different proportions of open and closed issues
- API rate limits and collection constraints
- Inconsistent usefulness of labels for supervised classification

These limitations will be evaluated during data collection and dataset construction.

## 9. Final Selection Decision

The initial candidate repositories for OpenSourceLens are:

1. `microsoft/vscode`
2. `pytorch/pytorch`
3. `kubernetes/kubernetes`
4. `huggingface/transformers`

They were selected to provide a substantial and diverse source of GitHub issue data.

Their suitability will be validated through actual data collection and exploration. If a repository does not provide sufficient usable data for a particular task, its contribution to that task will be limited or an alternative repository will be considered.

The project will not assume that every repository contributes equally to every machine-learning task.

## 10. Expected Outcome

The expected outcome of this step is a documented set of candidate repositories and an evaluation strategy for determining which collected issues are suitable for analytics, classification, related-issue detection, and resolution analysis.
