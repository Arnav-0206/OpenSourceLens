# OpenSourceLens — Benchmark Repositories & Generalization Strategy

## 1. Role of Benchmark Repositories vs. Production Scope

In OpenSourceLens, there is a fundamental distinction between the **benchmark repositories** and the **operational product**:

- **The Product:** A universal platform that dynamically ingests, analyzes, and extracts Data Science intelligence from **any eligible public GitHub repository** supplied by a user.
- **The Benchmark Datasets:** Four diverse, high-volume open-source repositories selected as initial sample datasets to explore data distributions, engineer features, train baseline models, fine-tune transformer networks, and calibrate statistical heuristics.

The four benchmark repositories do **not** define the product's boundary; they serve as our **ground-truth experimental laboratory**.

## 2. Selected Benchmark Repositories

The four offline benchmark repositories were selected for their domain diversity, high issue volume, rich discussions, and mature triage workflows:

| # | Repository | Domain | Volume Analyzed | Key Benchmark Role |
|---|---|---|---|---|
| 1 | `microsoft/vscode` | Developer Tools & IDE | 536 issues | High-velocity triage benchmark (rapid ~7.7h median closure, high duplicate volume) |
| 2 | `pytorch/pytorch` | Deep Learning Framework | 598 issues | High technical complexity benchmark (CUDA/autograd issues, complex reproduction steps) |
| 3 | `kubernetes/kubernetes` | Cloud Infrastructure | 599 issues | Distributed governance benchmark (multi-SIG labeling, prolonged ~141h consensus lifecycle) |
| 4 | `huggingface/transformers` | NLP & Generative AI | 595 issues | Rapid community iteration benchmark (community PR velocity, modern transformer issues) |

Together, these four repositories comprise **2,328 standardized GitHub issues**, providing a balanced cross-section of open-source software engineering dynamics.

## 3. Generalization Strategy

To ensure models and analytical pipelines generalize beyond the four benchmark repositories to unseen repositories, OpenSourceLens adheres to the following principles:

### 3.1 Domain-Agnostic Feature Engineering
- Feature extractors must rely on **structural and universal linguistic markers** rather than repository-specific keywords (e.g. word counts, code block presence, stack trace indicators, author relationship tags, punctuation patterns).
- Machine learning models must **not** include hardcoded repository one-hot dummy variables (e.g. `is_repo_vscode`) as predictive features in production inference, as these cannot generalize to novel repositories.

### 3.2 Open-Vocabulary Text Classification
- The fine-tuned **DistilBERT** sequence classifier uses a subword WordPiece vocabulary (30,522 tokens), allowing it to tokenize and categorize arbitrary programming jargon, error messages, and descriptions from unseen repositories into universal functional classes (`bug`, `feature`, `documentation`, `question`, `other`).

### 3.3 Universal Semantic Vector Space
- Semantic retrieval employs the pre-trained `all-MiniLM-L6-v2` Sentence-Transformer model, which maps issue titles and descriptions from **any** repository into a standardized 384-dimensional cosine similarity space without requiring per-repository retraining.

### 3.4 Non-Parametric & Adaptive Statistical Metrics
- Development velocity, Gini coefficients, contributor retention, and pull request survival curves adapt dynamically to the scale and history of the repository being analyzed.

## 4. Repository Eligibility & Threshold Criteria

When a user submits an arbitrary GitHub repository for analysis, OpenSourceLens evaluates the following eligibility criteria:

| Criterion | Minimum Threshold | Rationale |
|---|---|---|
| **Public Accessibility** | HTTP 200 via GitHub API | Private or deleted repositories cannot be accessed without user OAuth scopes |
| **Minimum Commit History** | $\ge 20$ commits | Ensures sufficient longitudinal data to compute meaningful activity trends and Gini coefficients |
| **Issue / PR Volume** | $\ge 10$ historical issues or PRs | Prevents empty distributions or division-by-zero errors in survival and resolution models |
| **Non-Fork Status** | Primary repository preferred | Forked repositories often mirror parent commit logs without maintaining local community triage |
| **Rate Limit Feasibility** | Within current API budget | Ensures full repository telemetry can be collected without exhausting rate limits |
